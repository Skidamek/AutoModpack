AutoModpack keeps its files in an `automodpack/` folder inside the game directory: the server root for a server, the instance folder for a client. This page writes that folder as `~/automodpack/`.

The one-shot client drop-in is `~/automodpack/automodpack-bootstrap.json`. It lives inside `automodpack/` so a pack cannot ship or overwrite it. Put a copy there, launch, and AutoModpack imports then deletes it. AutoModpack must already be installed. If the file includes `serverName`, import writes that entry into vanilla `servers.dat`. An `automodpack-bootstrap.json` in the instance root is ignored.

`/automodpack host bootstrap` writes `~/automodpack/automodpack-bootstrap.exported.json`. That file is not imported, so running the command on a logical server does not reroute the same instance. Copy it to a client as `automodpack-bootstrap.json`.

Files you edit sit at the top of the `automodpack/` folder. Runtime state lives in `client/`, `server/`, and the content store.

## You edit these

| Path | Role |
|---|---|
| `server-config.json` | Server settings |
| `client-config.json` | Client settings |
| `automodpack-bootstrap.exported.json` | Written by `/automodpack host bootstrap`. Copy to clients; this instance does not import it |
| `automodpack-bootstrap.json` | Client drop-in. Imported on launch, then deleted |
| `host-modpack/<group>/` | Extra pack files that are not already on the server. `main` is the default group |
| `patch-notes.md` | Notes for the next published generation. AutoModpack consumes the file when it publishes |
| `credentials/certificate.crt` | TLS certificate chain |
| `credentials/private-key.pem` | TLS private key, PKCS#8 PEM |
| `credentials/provisioning-secret` | Shared bootstrap download secret. Keep this folder off support dumps |

`recovered/` holds copies saved from the preservation vault. Do not put pack source files there.

The server cannot claim `player-local/`, `saves/`, `screenshots/`, `logs/`, or `automodpack/` itself. Put private client files under those roots if you need a folder the pack will not touch.

## AutoModpack manages these

Do not edit these by hand.

### Server runtime — `~/automodpack/server/`

The published history is one append-only journal: `journal.jsonl` lists every published generation with its patch notes, `current-projection.json` is the materialized view of the current one, `staging/` holds in-flight publishes, and `secrets.json` holds the per-player download secrets. Dedicated servers also keep their own content store under `data/`.

### Client runtime — `~/automodpack/client/`

| Path | Role |
|---|---|
| `active/` | The one live projection the loader reads |
| `history/<modpack-id>/` | The journal mirror for this pack: the server's generation timeline, so the History screen works offline |
| `overlays/<modpackId>/` | Player edits that survive generation switches |
| `baselines/`, `generated-copies/`, `incoming/`, `backup/`, `preservation/` | Update, repair, and loader-copy working state |
| `active-state.json`, `selections.json`, `restart-state.json`, `update-transaction.json`, `repair.json` | Pointers and in-flight work |

`automodpack/helper/` (outside `client/`) is where detached update and repair helpers log their runs.

### Content store

Downloaded and hosted bytes live in a content-addressed store, shared across Minecraft instances on the same user when possible:

- Linux: `~/.local/share/automodpack/data` (or `$XDG_DATA_HOME/automodpack/data`)
- macOS: `~/Library/Application Support/automodpack/data`
- Windows: `%LOCALAPPDATA%\automodpack\data`

A dedicated server always keeps its store inside the instance at `~/automodpack/server/data/`. A client shares the platform store with every other instance of the same user; when that root is not writable, the client falls back to its own instance-local `~/automodpack/client/data/`. Tests and isolated runs can set `AUTOMODPACK_DATA_ROOT` (or the `automodpack.data.root` system property); a configured root that cannot be used is an error, not a fallback.

The store contains Git-style objects (`objects/<aa>/<rest-of-sha1>`), file and mod metadata caches, per-pack `packs/<modpack-id>/connection.json`, and `known-hosts.json`.

## Server generation

The pack is built from `~/automodpack/host-modpack/<group>/` plus `syncedFiles` in [server config](../configuration/server-config). Both map to `~/.minecraft/` on the client.

Publishing writes generation history under `~/automodpack/server/`. Do not edit those files. Change config or `host-modpack/` and generate again.

## Client projection

The selected generation is materialized into the fixed path `~/automodpack/client/active/`. Immutable files are hard-linked from the content store when the filesystem allows it. Editable files use the overlay only after the player changes them.

The game directory receives live copies only for files the loader or game must read there. Standard `mods/` receives the AutoModpack loader, loader-required copies, and retained user-owned files. Instance-wide `pinnedModIds` keep matching live jars in that folder; AutoModpack still syncs the pack copies into the projection and skips loading them. There is no per-modpack client directory.

<Callout>
AutoModpack removes a live file only when its ownership ledger and content hash prove that the file is still managed by AutoModpack. User-owned or edited files are preserved.
</Callout>

### Why an active projection?

1. A bad update can be fixed remotely before the loader sees the mods, instead of crashing on launch in the standard `mods/` folder.
2. If an update is pending while you are not in-game, AutoModpack can apply it on the next launch before loading the pack, so you often do not need a second restart.
3. The projection path does not change with generation identity, so switching or recovering a generation rewires one tree instead of keeping one physical tree per pack.

Some loader services cannot be discovered from the projection. AutoModpack copies those files to standard `mods/` only when the loader-specific placement rule requires it.
